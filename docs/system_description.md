# Описание системы торговых роботов

## 1. Цель

Создать модульную платформу для разработки, бэктестинга и последующего запуска торговых роботов. Сейчас кодируется только слой рыночных данных; стратегия, риск-менеджмент и execution пока остаются целевой архитектурой.

## 2. Целевая архитектура

1. **Data Collection** — исторические и позднее потоковые данные.
2. **Instrument Catalog** — UID/FIGI/ticker, биржа, лотность, шаг цены.
3. **Data Quality** — дубли, пропуски, торговый календарь, аномалии.
4. **Feature Engine** — индикаторы и признаки.
5. **Strategy Engine** — сигналы.
6. **Backtesting** — воспроизведение истории и модель исполнения.
7. **Risk Management** — лимиты и контроль риска.
8. **Execution** — заявки и состояние исполнения.
9. **Portfolio** — позиции, cash, PnL, экспозиции.
10. **Monitoring/Audit** — логи, метрики, алерты, воспроизводимость решений.
11. **GUI / Operator Console** — локальное управление сбором данных, агрегацией, просмотром состояния и графиков.

Стратегия не должна зависеть от T-Invest или физического формата хранения данных.

## 3. Масштаб текущего data-модуля

Проектировать нужно не как демонстрационную базу, а как долговременное локальное хранилище:

- 30 акций;
- 5 лет;
- raw: 1m;
- derived: 15m, 30m, 1h.

При 500–600 торговых минутах в день это порядка 19–23 млн raw-записей. Реальный объём может быть выше из-за расширенных сессий и изменений расписания, поэтому система не закладывает фиксированное число минут в торговом дне.

Агрегаты добавят примерно 10% от числа raw-строк при полностью заполненных временных сетках (`1/15 + 1/30 + 1/60 ≈ 11.7%`), но фактическое отношение зависит от торговых сессий и пропусков.

## 4. Data Collection

### 4.1. Источник

T-Invest API `MarketDataService/GetCandles`.

### 4.2. Raw слой

Единственный внешний исторический таймфрейм системы — **1m**. Он является источником истины для более крупных интервалов.

Для каждого инструмента:

- первый запуск начинается с `collector.history_from`;
- следующие запуски — с последней raw-свечи минус overlap;
- конечная точка — текущее UTC-время;
- сохраняются только завершённые свечи;
- запросы режутся на окна до 24 часов;
- запись идемпотентна.

### 4.3. Точность

OHLC сохраняются как `int64` в наносах:

`price_nano = units * 1_000_000_000 + nano`.

`float` на raw-слое не используется.

## 5. Физическое хранение

### 5.1. Parquet data lake

Свечи хранятся в Parquet с Zstandard compression.

Ключ партиции:

`(timeframe, instrument_id, year, month)`.

Пример:

```text
data/market/1m/instrument_id=BBG.../year=2026/month=09/candles.parquet
```

Выбор месячной гранулярности даёт баланс:

- не создаёт десятки тысяч маленьких файлов;
- месячная партиция одного инструмента легко помещается в память при merge;
- overlap текущих данных требует переписать только один небольшой файл;
- пятилетняя история 30 акций даёт около 1 800 файлов на таймфрейм.

### 5.2. DuckDB catalog

`data/trading.duckdb` хранит только operational metadata и SQL-views:

- `partitions`: timeframe, instrument_id, year/month, row_count, first_time/last_time, dirty, updated_at;
- `system_metadata`: версия схемы каталога;
- `candles_1m`, `candles_15m`, `candles_30m`, `candles_1h`: views поверх Parquet.

История свечей физически в DuckDB не дублируется. DuckDB читает Parquet напрямую, поэтому тот же набор данных используется collector-ом, будущим DataFeed и аналитическими запросами без отдельной миграции. Если каталог удалён или создаётся заново при уже существующих Parquet-файлах, `initialize()` восстанавливает метаданные партиций из файлов; raw-партиции при таком восстановлении помечаются dirty для безопасной перестройки агрегатов.

### 5.3. Почему DuckDB

Для объёма порядка десятков миллионов свечей DuckDB используется как аналитический каталог, а не как единая таблица со всей историей. Это даёт SQL-доступ к Parquet, filter/projection pushdown и единый metadata layer без загрузки raw-истории внутрь БД. Запись operational state предполагается из одного collector-процесса; сетевые запросы к T-Invest в будущем можно распараллеливать отдельно.

### 5.4. Атомарность

При изменении месячной Parquet-партиции:

1. читается существующий месяц;
2. новые свечи merge-ятся по времени;
3. данные сортируются;
4. пишется временный файл;
5. `os.replace` атомарно заменяет целевой файл;
6. после успешной записи обновляется DuckDB-каталог.

## 6. Агрегаты 15m / 30m / 1h

Агрегаты не загружаются из T-Invest. Они производятся только из raw 1m.

Формулы:

- `open` = open первой минутной свечи;
- `high` = max(high);
- `low` = min(low);
- `close` = close последней минутной свечи;
- `volume` = sum(volume).

Интервалы выравниваются по UTC epoch. 15m: `:00/:15/:30/:45`, 30m: `:00/:30`, 1h: начало часа.

В DuckDB-каталоге каждая изменённая месячная raw-партиция получает `dirty=TRUE`. После `collect` агрегатор берёт только dirty-месяцы, пересчитывает для них все включённые таймфреймы и затем снимает dirty-флаг. Если процесс упал до снятия флага, повторный запуск безопасно пересчитает тот же месяц ещё раз.

Полная команда `aggregate --all` позволяет удалить смысловую зависимость от старых алгоритмов агрегации: после изменения правил все derived datasets можно воспроизвести из raw.

## 7. Data quality, которую нужно добавить следующим шагом

Для 5-летней базы особенно важны:

- календарь торгов MOEX и изменения торговых сессий по датам;
- детектор неожиданных дыр внутри открытой сессии;
- различение «нет торгов» и «данные потеряны»;
- контроль OHLC-инвариантов (`low <= open/close <= high`);
- отрицательные/аномальные объёмы;
- отчёт покрытия по инструменту и месяцу;
- checksum/manifest партиции для контроля повреждений;
- корпоративные действия отдельно от raw-цен (не переписывать raw историю adjusted-значениями).

## 8. Контракты кода

### `TInvestMarketDataClient`

HTTP, rate limiting, retry и преобразование ответа API в `Candle`.

### `HistoricalCandleCollector`

Оркестрация пятилетней дозагрузки по инструментам и дневным API-окнам.

### `ParquetCandleStorage`

Raw/derived Parquet, месячный merge, atomic replace, DuckDB catalog, SQL views и dirty partitions.

### `AggregateBuilder`

Пересчёт 15m/30m/1h только из raw 1m.

### `GUI / Operator Console`

Streamlit-интерфейс является presentation-layer и вызывает те же application-компоненты, что и CLI. Он не содержит отдельной бизнес-логики хранения или агрегации. На текущем этапе GUI позволяет:

- видеть состояние Parquet/DuckDB datasets;
- запускать historical collection по выбранным инструментам;
- запускать incremental/full aggregation;
- читать свечи через `ParquetCandleStorage.query_candles()`;
- визуально контролировать последние данные.

GUI не изменяет YAML-конфигурацию автоматически и не хранит API token.

## 9. Правила будущей разработки

- Всё время — timezone-aware UTC.
- Raw market data не изменяется индикаторами/стратегиями.
- Derived данные всегда должны быть воспроизводимы из raw.
- Секреты не коммитятся.
- Любая загрузка и агрегация идемпотентна.
- Стратегия читает DataFeed API, а не файлы и не T-Invest напрямую.
- Backtest и live используют одинаковые доменные структуры свечей.
- Execution отделён от Strategy.
- Схемы и алгоритмы агрегации версионируются при несовместимых изменениях.
